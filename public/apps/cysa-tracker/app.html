Domain 1: Security Operations (~34%)

1.1 System & Network Architecture High Yield ▼
Big Idea: You cannot spot abnormal until you know what normal looks like. This is the raw material of SOC work — logs, OS, networks, identity.
Exam Trap: The cloud provider secures the cloud (hardware/hypervisor). YOU secure what is IN the cloud (data, configs, identities). Most cloud breaches = customer misconfiguration (open S3 buckets).
Exam Trap: Container images inherit vulnerabilities from base layers. One poisoned base image compromises every container built from it. Scan before deployment (Trivy).
Windows Event IDs to know cold: 4624 (success logon), 4625 (failed), 4672 (admin logon), 4688 (process creation — enable command-line auditing!), 4698 (scheduled task), 7045 (new service), 1102 (log cleared = anti-forensics). Logon Type 3 = network (lateral movement); Type 10 = RDP.
Linux: /var/log/auth.log (auth), /var/log/secure (RHEL), /etc/shadow (password hashes — root-only), /tmp & /dev/shm (malware staging, fileless execution).
1.2 Analyze Indicators of Potentially Malicious Activity PBQ Heavy ▼
IOC vs IOA: IOC = evidence left behind (hash, IP, domain) — reactive. IOA = behavior in progress (Office spawning PowerShell) — proactive. EDR focuses on IOAs because attackers rotate IOCs constantly.
Exam Trap: SPF/DKIM/DMARC passing does NOT mean an email is safe. A properly configured lookalike domain passes all three. Always check if the authenticated domain is the CORRECT domain.
Exam Trap: DNS tunneling indicators: abnormally long subdomains, high-entropy strings, high volume of DNS queries from a single host. Monitor Sysmon Event ID 22 for DNS queries.
LOLBins: PowerShell (-enc, -nop, -w hidden), certutil (-urlcache -split -f), mshta, regsvr32, wmic. The binary is trusted; the behavior is suspicious.
1.3 Use Tools to Determine Malicious Activity Tool Recognition ▼
Exam Trap: SIEM aggregates/correlates/alerts; SOAR orchestrates automated response. If the scenario says "automate the response/playbook," the answer is SOAR, not SIEM.
Exam Trap: Zeek generates behavioral logs WITHOUT signature rules. Snort/Suricata fire signature-based alerts. The exam tests this distinction directly.
Snort rule anatomy: alert tcp $EXTERNAL_NET any -> $HOME_NET 80 (msg:"WEB ATTACK"; content:"/etc/passwd"; sid:1000001;). Action + Protocol + Src -> Dst + Options. IPS mode uses "drop" not "alert."
1.4 Threat Intelligence & Threat Hunting ▼
Pyramid of Pain: Bottom = Hash Values (trivial to change). Top = TTPs (forces attacker to change how they operate). Detecting at TTP level = most durable defense.
Threat Hunting Loop: 1) Hypothesis (driven by intel, TTP, or anomaly), 2) Data Collection, 3) Analysis (confirm/refute), 4) Response/Documentation. A hunt that finds nothing but improves detection rules is still a success.
1.5 Efficiency & Process Improvement SOAR Focus ▼
Exam Trap: Standardize first, then automate. You cannot automate chaos. If a SOC has inconsistent handling, the answer is standardization before SOAR deployment.
1.6 AI in Security Operations V4 New ▼
Exam Trap: AI proposes; humans validate and own decisions. The biggest liability in 2026 is an analyst who trusts AI output without questioning it. Always verify AI-generated IOC claims.
Indirect Prompt Injection: Attacker embeds malicious instructions in documents/emails that an AI tool later processes. Never feed raw attacker-controlled content into an AI assistant without sanitization.

Domain 2: Vulnerability Management (~26%)

2.1 Vulnerability Scanning Methods High Yield ▼
Big Idea: A vulnerability is a weakness; a threat is what exploits it; risk = likelihood × impact. Most breaches exploit known, unpatched vulnerabilities.
Exam Trap: A scenario with very few findings on a known-vulnerable host almost always means a non-credentialed scan was used. Credentialed scans produce 10× more findings.
Exam Trap: OT/ICS/SCADA systems can crash under active scanning. The correct answer is passive monitoring or purpose-built tools (Claroty, Dragos, Nozomi Networks), never standard aggressive scanning.
Scan Choice Matrix: I-C-A-P-D-B = Internal/External, Credentialed, Agent-based, Passive, Discovery, Baseline.
2.2 Vulnerability Assessment Tools Tool ID ▼
Tool Differentiation: Burp/ZAP = intercepting proxies for manual app hacking. Nikto = automated server scan only. Nessus = infrastructure vuln scanner. Nuclei = fast template-based external scanner. BloodHound = AD attack path mapper.
Exam Trap: Metasploit is listed under multipurpose tools for the exam — it tests scanning, enumeration, and validation use cases, not just exploitation. All usage requires written authorization.
2.3 Prioritize & Mitigate Vulnerabilities CVSS/EPSS ▼
Exam Trap: "Patch the highest CVSS first" is usually WRONG. The tested answer weighs business context, exposure, and active exploitation. KEV-listed = immediate priority regardless of raw CVSS.
Exam Trap: CVSS alone has no business context. Environmental metrics (asset criticality) convert a score into a remediation order. A 9.8 on an isolated lab box matters less than a 6.5 on your internet-facing payment server.
Risk Responses: A Tiger Ate Me = Accept, Transfer, Avoid, Mitigate. SLE = AV × EF. ALE = SLE × ARO.
2.4 Control Types, Risks & App Security ▼
Exam Trap: Security awareness training delivered via digital platform is still an ADMINISTRATIVE control (people/policy), not technical. Classify by purpose, not delivery method.
Exam Trap: Do not confuse preventative (blocks) with detective (observes). A firewall that blocks traffic = preventative. An IDS that alerts on traffic = detective. An IPS that drops traffic = responsive/preventative hybrid.
Secure SDLC: Requirements → Design (STRIDE threat modeling) → Development (SAST, code review) → Testing (DAST, pen test) → Deployment (hardened images) → Maintenance (patching). The earlier security is baked in, the cheaper the fix.

Domain 3: Incident Response & Management (~24%)

3.1 Attack Methodology Frameworks Know Cold ▼
Kill Chain Mnemonic: "Real Weapons Deliver Explosive Installations Causing Actions" = Recon, Weaponization, Delivery, Exploitation, Installation, C2, Actions on Objectives.
Key distinction: Kill Chain = sequence of an attack; ATT&CK = catalog of techniques; Diamond = relationships in a single intrusion event. The exam asks you to map observed behavior to the correct framework element.
3.2 Incident Response Lifecycle (NIST SP 800-61) PICERL ▼
Exam Trap: The #1 tested process error is jumping to eradication before containment. First action on malware detection = CONTAIN (isolate), not remove. You put out the fire's spread before rebuilding the house.
Exam Trap: Re-image = eradication (remove the threat), NOT recovery. Recovery is restoring to production safely AFTER the threat is gone. Do not skip eradication of the exploited vulnerability before recovery.
Order of Volatility (RFC 3227): Collect most-volatile first: CPU registers/cache → RAM → Network state → Swap/pagefile → Disk/SSD → Remote logs → Printouts. Memory before you pull the plug!
Evidence Handling: Chain of custody (documented who/what/when/where — breaks make evidence inadmissible), forensic imaging (bit-for-bit copy with SHA-256 hash), write blockers, legal hold (preserve everything once litigation is anticipated).
3.3 Implement Incident Response Scenario Heavy ▼
Exam Trap: Isolating a device via EDR preserves volatile memory and maintains the EDR channel. Powering off destroys RAM evidence. In active incidents, choose isolation over shutdown.
Exam Trap: In OT/ICS environments, isolating a device without operations coordination can cause uncontrolled process shutdowns more dangerous than the attack itself. Notify operations first.

Domain 4: Reporting & Communication (~16%)

The smallest domain, but many candidates under-prepare and lose unexpected points here. Budget real study time.

4.1 Vulnerability Management Reporting Audience Matters ▼
Exam Trap: Rising vulnerability counts do NOT automatically mean worsening security. Expanded scan coverage increases finding counts. Always provide context with trend data.
Audience Rule: Match depth and language to the reader. Board members get business impact + trends + resource needs (no jargon). Technical teams get IOCs, evidence, and remediation steps.
4.2 IR Reporting & Communication Scenario Judgment ▼
Exam Trap: "Tell only IT" about a breach is often the wrong answer. Regulatory/legal notification timelines exist. Ignoring them = compliance violation. The correct answer involves proper stakeholder notification through defined channels.
Exam Trap: Communication IS a containment step. Notifying the right stakeholder fast is part of incident response. Delaying communication to "avoid panic" often backfires.
Mean-Time Family: MTBF = time BETWEEN failures (reliability). MTTD = to DETECT. MTTA = to ACKNOWLEDGE. MTTR = to RESPOND/repair. Dwell time = how long attacker was inside before detection.

Email Authentication Trio

SPF — Sender Policy Framework. DNS TXT record listing authorized sending IPs. SPF checks the ENVELOPE sender (Return-Path). Fail = sending server not authorized.
DKIM — DomainKeys Identified Mail. Cryptographic signature on outgoing email. Pass = message came from a server holding the private key and was not modified in transit.
DMARC — Domain-based Message Authentication, Reporting, and Conformance. Sits on top of SPF+DKIM. Adds alignment checking (Display From must match what passed SPF/DKIM). Policy: none (monitor), quarantine, reject.
Trap: A properly configured lookalike domain passes SPF, DKIM, AND DMARC. Authentication catches SPOOFED domains, not convincing lookalikes. Always verify the actual domain name.

Real-World Scenarios & Case Studies

Practice reasoning through these. The exam rewards correlating across sources, not single-alert reading.

Scenario 1: Phishing → BEC Investigation

Alert: User reports suspicious email from "CEO" requesting urgent wire transfer. Display name says "CEO" but actual sending address is external lookalike domain.

Your Steps:

  1. MXToolbox header analysis: Check SPF (sending IP authorized?), DKIM (signature valid?), DMARC (alignment?).
  2. WHOIS the domain: registration date <30 days? Privacy protection? Generic name servers?
  3. Check for inbox rules created by the user (auto-delete sent items, auto-forward) — account takeover BEC indicator.
  4. UEBA check: Any impossible travel on this account? New device? Off-hours login?
  5. If ATO confirmed: Disable account, revoke all sessions/tokens, force password reset, check proxy logs for data exfiltration.
  6. If impersonation only: Block domain, pull all similar emails from mail gateway, notify users of campaign.
Key Distinction: Impersonation BEC = fraud investigation (block, notify). Account Takeover BEC = active compromise (contain, reset, full IR).

Scenario 2: Ransomware IR

Alert: EDR detects mass file renames + ransom note on endpoint. Multiple hosts showing same behavior.

Your Steps (PICERL):

  1. Containment: EDR network isolation on all affected hosts immediately. Do NOT power off (preserves RAM for forensics). Disable compromised service accounts.
  2. Scope: SIEM query for Event ID 4688 (process creation) looking for vssadmin delete shadows, wmic shadowcopy delete, or PowerShell encoding. Check lateral movement (Event 4624 Type 3).
  3. Eradication: Re-image affected systems from known-good gold images. Patch the initial entry vulnerability (likely unpatched RDP or phishing). Remove all persistence (scheduled tasks, services, registry Run keys).
  4. Recovery: Restore from offline backups (ransomware targets online backups first). Validate clean before reconnecting. Monitor for re-infection 24-72 hours.
  5. Post-Incident: RCA — why did initial access succeed? Missing MFA? No EDR on that segment? Update detection rules for the TTPs observed.
Trap: Starting with eradication before containment lets the ransomware spread while you clean. Always contain first.

Scenario 3: Vulnerability Prioritization

Context: Scanner reports 500 findings. You have 2 staff and 1 week. Three sample findings:

  • CVE-A: CVSS 9.8, internet-facing web server, no known exploitation, patch available.
  • CVE-B: CVSS 6.5, internal domain controller, listed on CISA KEV (active exploitation confirmed), patch available.
  • CVE-C: CVSS 7.2, isolated test lab, no known exploitation, no patch yet.

Your Priority Order:

  1. CVE-B first. KEV-listed = attackers are using it NOW. Domain controller = highest asset value. Even though CVSS is lower, active exploitation on a critical asset = P0.
  2. CVE-A second. High CVSS + internet-facing = high risk, but no active exploitation means slightly lower urgency than KEV.
  3. CVE-C third. No patch = compensating controls only (segmentation, monitoring). Isolated = limited blast radius. Document exception with review date.
Rule: The highest CVSS is often the DECOY answer. Circle the internet-facing/business-critical/KEV-listed one instead.

Scenario 4: Cloud Misconfiguration → Data Exposure

Alert: ScoutSuite report shows S3 bucket "company-backups" changed from private to public. CloudTrail shows IAM user "dev-temp" made the change at 2AM from an unusual IP.

Your Steps:

  1. Immediate: Revert S3 ACL to private. Check S3 access logs for any unauthorized GetObject operations.
  2. Investigate IAM user "dev-temp": Is this a legitimate account? When created? Any other API calls (AssumeRole, CreateAccessKey)?
  3. GuardDuty correlation: Any findings for this IP? Exfiltration:S3/AnomalousBehavior?
  4. Contain: Disable "dev-temp" keys, revoke sessions. Check for IAM policy changes that expanded permissions.
  5. Scope: Which data was in the bucket? PII? CHD? PHI? This drives regulatory notification requirements (GDPR 72h, state laws).
  6. Fix: AWS Config rule s3-bucket-public-read-prohibited. SCP to prevent public S3 at org level. Least-privilege IAM review.
Cloud Correlation Triad: CloudTrail (who did what), GuardDuty (behavioral anomalies), Config (configuration drift). Always correlate all three.

Scenario 5: Insider Threat / Data Exfiltration

Alert: UEBA flags employee in Finance: 3AM login from home country (normal), but then bulk download of 10,000 customer records to personal OneDrive via PowerShell.

Your Steps:

  1. Do NOT confront the user immediately — this triggers destruction of evidence or legal complications.
  2. Preserve: Legal hold on mailbox, logs, and endpoint. Capture EDR telemetry and memory image before the next shift.
  3. Contain: Disable account quietly during business hours (avoiding tip-off). Revoke all active sessions. Block personal OneDrive domain at proxy.
  4. Investigate: DLP logs for prior exfiltration attempts. Check USB device history (Event 6416). Review recent resignation notices or performance issues.
  5. Escalate: HR and Legal must be involved before any technical action that could be construed as employment action. Chain of custody for all evidence.
  6. Post-Incident: Review DLP policies (why didn't it block?). UEBA threshold tuning. Access review — did this user need 10K records for their role?
Trap: Intentional insider threats require HR/Legal escalation BEFORE technical containment if possible. Unintentional insiders (negligence) require training and process fixes. Know which type the scenario describes.
